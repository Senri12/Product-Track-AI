# Интеграция через сессии и администрирование

Документ описывает концептуальную архитектуру интеграции системы сессий для образовательного AI-ассистента и предложения по администрированию (лимиты запросов, хранение диалогов, режимы закрытия системы).

## 1. Интеграция через сессии — концепция

Идея: при выборе раздела студентом создаётся изолированная сессия, в которую загружаются системный промпт и контекст данной лекции. Сессии обеспечивают фокус на материале раздела, позволяют сохранять локальное состояние обучения и управлять потреблением ресурсов.

- При выборе раздела:
  - Создаётся новая сессия с уникальным идентификатором.
  - Подгружается специфичный для раздела системный промпт (правила поведения ассистента, ограничения, стиль объяснений).
  - Загружается контекст лекции: текст, ключевые темы, упражнения, примеры и т. п.
  - Сессия хранит метаданные: userId, sectionId, время создания, статус и счётчик запросов.

- Во время работы:
  - Все входящие и исходящие сообщения привязаны к сессии.
  - При отправке запроса LLM получает: системный промпт раздела + релевантный контекст + историю диалога (в разумных пределах).
  - Агент ориентирован оставаться в рамках раздела; при уходе в сторону — мягкое возвращение к теме.
  - Контекст и системный промпт подгружаются один раз при создании сессии (для экономии), а при необходимости обновляются явно.

- Завершение и возобновление:
  - Студент или система может закрыть сессию (статус `closed`).
  - Сессии могут иметь срок жизни (timeout/expiration).
  - При необходимости пользователь может возобновить сохранённую сессию, если не истёк срок хранения.

## 2. Администрирование — ключевые аспекты

Цели администрирования: предотвращение злоупотреблений, контроль затрат на LLM, обеспечение справедливого доступа и защита академической честности (особенно перед дедлайнами и экзаменами).

### A. Ограничение количества запросов

Подход: многоуровневые лимиты с комбинированными правилами.

- Типы лимитов:
  - На сессию (например, 30–100 запросов/сессия) — ограничивает глубокое взаимодействие в одном разделе.
  - На пользователя в час (например, 20–50) — защита от пиков активности и ботов.
  - На пользователя в день (например, 100–200) — общий потолок потребления.
  - Глобальные QPS/Throughput лимиты для всей системы (инфраструктурная защита).

- Поведение при достижении лимита:
  - Мягкие уведомления за N оставшихся запросов.
  - Блокировка новых сообщений при исчерпании лимита с объяснением (и возможностью запроса продления/покупки дополнительного пакета).
  - Различать временные блокировки и постоянные (например, для нарушителей).

- Гибкость:
  - Разные лимиты для ролей: студент/преподаватель/админ.
  - Политики для экзаменов: временное ужесточение лимитов или полное ограничение генерации ответов.

### B. Хранение диалогов

Что хранить и почему:
- Полный лог сообщений (роль, текст, метки времени).
- Метаданные: sectionId, sessionId, userId, использованные токены, версия системного промпта.
- Агрегированные данные: статистики по теме, частые вопросы, ошибки ассистента.

Зачем:
- Для возврата студенту к предыдущим сессиям и повторения материала.
- Для преподавателей: анализ успеваемости, определение сложных тем.
- Для разработчиков: улучшение промптов, обнаружение багов и недочётов поведения агента.
- Для соответствия требованиям (аудит, модерация, спорные ситуации).

Хранение и срок:
- Активные сессии: живут пока студент/курс активны.
- Архив: хранить дольше (например, 6–12 месяцев), с возможностью сжатия/анонимизации.
- Соответствие законодательству о данных — возможность удаления по запросу, управление персональными данными.

### C. Закрытие системы перед дедлайном (режимы и сценарии)

Причины: предотвратить списывание во время экзаменов, выполнить техработы, завершить курс.

Варианты режимов:
- Полное закрытие: никто не может отправлять запросы (доступ только для админов).
- Режим "только чтение": просмотр истории доступен, но новые запросы запрещены.
- Ограниченный доступ: разрешено только для определённых разделов или ролей.
- Плавное закрытие: оповещения заранее (неделя/день/час), после чего применяется выбранный режим.

Управление:
- Панель администратора для включения/выключения режимов по расписанию или вручную.
- Белые/чёрные списки пользователей (например, преподаватели всегда имеют доступ).
- Логирование всех событий закрытия и попыток обращения во время закрытия (аудит).

## 3. Дополнительные рекомендации и фичи

- Аналитика: отчёты по сложным темам, времени на решение задач, активности студентов.
- Экономика использования LLM: метрики токенов/стоимости по сессиям, отчёты для управления бюджетом.
- Безопасность: модерация контента, детектирование злоупотреблений и API-ключей.
